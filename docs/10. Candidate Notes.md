## 1. Elevator Pitch

**The Problem:** A development team maintains a movie catalog web application with a React frontend and Flask backend, but lacks automated testing, building, and deployment workflows. Every release requires manual steps, leading to slow iteration cycles and inconsistent deployments.

**The Solution:** A complete CI/CD pipeline using GitHub Actions that automates linting, testing, Docker image building, ECR push, and EKS deployment via Kustomize. Infrastructure is provisioned with Terraform (VPC, EKS cluster, ECR repositories, IAM users), and Kubernetes manifests use Kustomize for dynamic image tagging.

**The Result:** Four GitHub Actions workflows handle the full lifecycle:

- **Frontend CI** / **Backend CI**: Triggered on PRs to `main`, running lint, test, and build jobs in parallel/sequence
- **Frontend CD** / **Backend CD**: Triggered on push to `main`, building Docker images tagged with git SHA, pushing to ECR, and deploying to EKS via Kustomize

## 2. Architecture & Design Decisions

### Module Map

```txt
┌───────────────────────────────────────────────────────────────────────┐
│                    GitHub Actions Workflows                           │
│  frontend-ci.yaml  backend-ci.yaml  frontend-cd.yaml  backend-cd.yaml │
└──────────────────────────────┬────────────────────────────────────────┘
                               │ triggers on PR/push
                               ▼
┌──────────────────────────────────────────────────────────────┐
│                     Application Code                         │
│  starter/frontend/ (React)    starter/backend/ (Flask)       │
│  - ESLint + Jest              - flake8 + pytest              │
│  - Dockerfile (node:alpine)   - Dockerfile (python:slim)     │
│  - k8s/kustomization.yaml     - k8s/kustomization.yaml       │
└──────────────────────────────┬───────────────────────────────┘
                               │ docker build + push
                               ▼
┌──────────────────────────────────────────────────────────────┐
│                     Amazon ECR                               │
│  frontend repository         backend repository              │
│  (image tagged with git SHA)                                 │
└──────────────────────────────┬───────────────────────────────┘
                               │ kustomize edit set image
                               ▼
┌──────────────────────────────────────────────────────────────┐
│                     Amazon EKS                               │
│  cluster: "cluster" (Kubernetes 1.34)                        │
│  Node group: "udacity" (t3.small)                            │
│  Deployments: frontend (port 3000) + backend (port 5000)     │
│  Services: LoadBalancer type (external access)               │
└──────────────────────────────────────────────────────────────┘
```

### Key Architectural Decisions

| Decision | Rationale |
| :--- | :--- |
| **Separate CI and CD workflows** | CI validates PRs (lint + test + build), CD deploys on merge to main. Separation allows testing without deploying. |
| **Path-based triggers** | Frontend workflows only run when `starter/frontend/**` changes, avoiding unnecessary builds. |
| **Git SHA tagging** | Every Docker image is tagged with `${{ github.sha }}` for traceability and rollback. |
| **Kustomize for deployments** | Dynamic image tag injection via `kustomize edit set image` avoids hardcoding tags in manifests. |
| **Secrets over hardcoded values** | All AWS credentials and ECR repo names stored as GitHub Secrets — no hardcoded account IDs or keys. |
| **`pipenv install --dev`** | Dev dependencies (flake8) are required for linting; standard `pipenv install` omits them. |
| **Debian-based Python image** | Alpine's musl libc caused `uwsgi` compilation failures; `python:3.10-slim` resolves this. |

## 3. CI/CD Pipeline Design

### Frontend CI (`frontend-ci.yaml`)

| Job | Depends On | Steps |
| :--- | :--- | :--- |
| **Lint** | — | checkout → setup-node (.nvmrc) → cache → npm ci → npm run lint |
| **Test** | — | checkout → setup-node (.nvmrc) → cache → npm ci → CI=true npm test |
| **Build** | lint, test | checkout → setup-node (.nvmrc) → cache → npm ci → docker build |

### Backend CI (`backend-ci.yaml`)

| Job | Depends On | Steps |
| :--- | :--- | :--- |
| **Lint** | — | checkout → setup-python (3.10) → pip install pipenv → pipenv install --dev → pipenv run lint |
| **Test** | — | checkout → setup-python (3.10) → pip install pipenv → pipenv install --dev → pipenv run test |
| **Build** | lint, test | checkout → docker build |

### Frontend CD (`frontend-cd.yaml`)

| Job | Depends On | Steps |
| :--- | :--- | :--- |
| **Lint** | — | (same as CI) |
| **Test** | — | (same as CI) |
| **Build** | lint, test | checkout → configure-aws-credentials → ecr-login → docker build (with REACT_APP_MOVIE_API_URL) → docker push |
| **Deploy** | build | checkout → configure-aws-credentials → ecr-login → eks update-kubeconfig → kustomize → kubectl apply |

### Backend CD (`backend-cd.yaml`)

| Job | Depends On | Steps |
| :--- | :--- | :--- |
| **Lint** | — | (same as CI) |
| **Test** | — | (same as CI) |
| **Build** | lint, test | checkout → configure-aws-credentials → ecr-login → docker build → docker push |
| **Deploy** | build | checkout → configure-aws-credentials → ecr-login → eks update-kubeconfig → kustomize → kubectl apply |

## 5. Challenges & Resolutions

### Challenge 1: Terraform Kubernetes Version Not Supported

**Symptom:** `InvalidParameterException: unsupported Kubernetes version 1.25`

**Root Cause:** The original Terraform specified Kubernetes 1.25, which AWS EKS deprecated. The Udacity lab environment only supports versions 1.34, 1.35, and 1.36.

**Fix:** Updated `variables.tf` to `default = "1.34"`. Also discovered the lab environment uses a newer AWS provider than the original Terraform expected, requiring an upgrade from `hashicorp/aws` 4.55.0 to `~> 5.0`.

### Challenge 2: IAM Permissions for Terraform

**Symptom:** `AccessDenied: User is not authorized to perform: iam:PutUserPolicy`

**Root Cause:** The Udacity Cloud Gateway role (`voclabs`) doesn't have permission to create IAM inline policies.

**Fix:** Removed the `aws_iam_user_policy.github_action_user_permission` resource from Terraform. Created the policy manually in AWS Console and attached it to `github-action-user`.

### Challenge 3: `flake8` Not Found in Backend CI

**Symptom:** `/bin/sh: 1: flake8: not found`

**Root Cause:** `pipenv install` doesn't install dev dependencies by default. `flake8` is in `[dev-packages]`.

**Fix:** Changed `pipenv install` to `pipenv install --dev` in both `backend-ci.yaml` and `backend-cd.yaml`.

### Challenge 4: `uwsgi` Fails to Compile on Alpine

**Symptom:** `error: passing argument 2 of 'signal' from incompatible pointer type`

**Root Cause:** `uwsgi` 2.0.21 has C compilation issues with newer Alpine Linux musl libc.

**Fix:** Changed base image from `python:3.10-alpine` to `python:3.10-slim` (Debian-based), which uses glibc and compiles `uwsgi` successfully.

### Challenge 5: Trailing Whitespace Lint Errors

**Symptom:** `W291 trailing whitespace` in Python files

**Root Cause:** Import statements in `__init__.py` and `movies_api.py` had trailing spaces.

**Fix:** Removed trailing whitespace from `starter/backend/movies/__init__.py` and `starter/backend/movies/movies_api.py`.

### Challenge 6: Windows Environment Compatibility

**Symptom:** `init.sh` (bash script) can't run on Windows; `export` command not recognized.

**Root Cause:** The project was designed for Linux (Udacity workspace), but running on Windows 11.

**Fix:** Created `init.ps1` (PowerShell equivalent), manually ran `aws-iam-authenticator` steps, and used `kubectl patch` to add the IAM user to Kubernetes `aws-auth` ConfigMap.

## 7. Retrospective

### What I'd Do Differently

1. **Check Kubernetes version availability first.** The version mismatch consumed significant time. Running `aws eks describe-cluster-versions` before writing Terraform would have prevented multiple failed apply attempts.
2. **Use Debian-based Python images from the start.** Alpine compatibility issues with compiled Python packages (uwsgi) are a known pain point — defaulting to `slim` avoids surprises.
3. **Pin Terraform provider versions more carefully.** The jump from AWS provider 4.55.0 to 5.x introduced schema differences that required manual state manipulation.

### What Worked Well

1. **Path-based triggers** saved CI minutes by only running relevant workflows.
2. **Kustomize image editing** provided a clean way to inject dynamic tags without templating.
3. **Secrets management** ensured no credentials were ever committed to the repository.
4. **Parallel lint/test jobs** in CI reduced feedback time significantly.

### Key Takeaway

> "Infrastructure as Code is only as good as your environment's actual constraints. The Udacity lab's restricted Kubernetes versions and IAM permissions meant the provided Terraform needed real-world adaptation — exactly the kind of debugging a DevOps engineer faces in production."
